## 1. 方向一（IM 客户端 SDK）资产复用盘点 —— 接口级确认

| 方向一能力 | 现状资产 | 复用程度 |
|---|---|---|
| 私有二进制协议 / 粘包分包 | `LengthHeaderCodec`（[length_header_codec.cpp](../include/net/length_header_codec.cpp)）4 字节大端长度 + payload | **直接搬**（若协议要含 type/seq，加字段即可）|
| 心跳 Keep-Alive | TcpConnection 空闲超时自续（runAfter 单次自续，跑通已验证）| **移植**（client 侧同逻辑）|
| 跨线程投递 | `EventLoop::runInLoop` + pendingFunctors + eventfd（[event_loop.cpp](../include/net/event_loop.cpp)）| **模式复用**（改成投外部队列，不动内核）|
| 连接生命周期 | shared_ptr 保活 + 回归属线程析构（已实战修过 bad_weak_ptr）| **模式复用** |
| 定时器 / 重试时间轴 | runAfter / runEvery / cancel | **直接搬** |
| socket / 非阻塞 / ET 读取 | Socket / Channel / Buffer | **直接搬**（client 只多一次 connect 调用）|

**结论：方向一的骨架 80% 是搬运，不是新写。** 它的新含金量集中在 3 处（见下）。

## 2. 方向一新写的 3 个核心难点（真正的面试价值）

### 2a. 断线指数退避重连 — 难度中，面试必问
- 重连间隔按 1s → 2s → 4s → …封顶(如 30s)，加随机抖动防「羊群重连」。
- 需要：`runInLoop` 调度未来的 connect 尝试 + 每次尝试失败后重排下一次（用 runAfter 单次自续——和心跳同一招）。
- 关键边界：**重连和「用户主动退出」必须互斥**。退出标志 → 取消所有 pending 重连,否则析构后回调悬垂（你 server 端已有同型训练）。

### 2b. 序列号 + 去重 / ACK — 难度中高，IM 协议层核心
- 每个消息带 `seq`；发方缓存未 ACK 消息，收方按 seq 去重、回 ACK。
- 重传：ACK 超时 → 重发（和定时器组合）。
- 去重表：`std::unordered_map<seq,msg>` 或小窗口 + 游标。**这正是 kv-engine 跳表可做「滑动窗口/去重」的接口落点**（回到方案 B）。

### 2c. 网络线程 → 外部主线程的消息投递 — 难度中，面试贯穿始终
- server 的 pendingFunctors 是**线程内部**中转；client 要投到**调用方自己的线程/队列**。
- 方法：client 暴露 `setMessageListener(cb)`,内部回调用「加锁 + 双缓冲队列（swap 模式，同 EventLoop::dopendingFunctors）」攒批,由调用方轮询/唤醒取走。
- 生命周期：listener 里要**断注册**（观察者注销）,避免「回调时外部对象已析构」——和 2a 的死锁式边界对齐。

## 3. 对比齐平运行（依据）

| 维度 | 方向一（IM SDK） | kv-engine（跳表存储）|
|---|---|---|
| 与已有资产相关度 | **极强**（80% 搬运）| **弱**（全新项目）|
| 新知识点 | 重连/退避、ACK/去重、观察者安全注销 | 跳表、WAL、并发锁 |
| 面试契合度 | server + client 完整故事，贴近企业 IM（飞书等）| Redis ZSet/AOF/缓存穿透考点 |
| 完成时间估计 | 3–5 天可出 TCP 版（QUIC/FEC 除外）| 3–5 天 |
| 失败风险 | 依赖 server 资产复用的正确性 | 独立，风险更低 |
| 建议顺序 | **在 kv-engine 之后**（理由见 §4）| **先做,或** 与 IM 串联后做「消息历史子模块」|

## 4. 明确取舍建议

**推荐顺序：kv-engine 先做（短、独立、稳），方向一(IM 客户端 SDK)次之，期间 server 端补「中继业务」.**

理由（一条主线，避免 scope 蔓延）：
1. **地基先夯实**：方向一的列表 — 尤其 ACK/去重 — 恰好能用「跳表 + 序列号」做更深的实现。先写跳表,方向一的「去重表」就不是临时造轮子，而是「我自研的存储引擎的应用」— 面试点 = 两段故事互相支撑。
2. **方向一的搬运依赖 server 稳定性**：先让 Kv 引擎独立验收(保底成果),再回接就降低「两件事同时半成」的风险。
3. **时间预算互不挤压**：6~10 天内只推进一条主线,产出可控。

**若你更想先做方向一**（例如面试刚好撞上 IM 岗），也可直接把 kv-engine 压后到「方向一完成后,再回 server 做消息历史子模块」。两条路线都可行,但**不要并行推进两个新仓库**。

## 5. 方向一里程碑拆分（若选它,按此作为同学的执行计划）

- Day1：client 版 `TcpClient`（connect + 复用 LengthHeaderCodec + 移动端 Buffer 复用）→ 能连上 server 回显。（P0）
- Day2：心跳 + 断线检测 + 指数退避重连（runAfter 自续）。（P0）
- Day3：私有协议加 type/seq 字段 → ACK/去重/重传。（P0）
- Day4：网络线程 → 外部队列投递 + 观察者安全注销。（P1）
- Day5：server 端中继(广播/转发) 打通端到端回显外的真实业务 + 面试整理。（P1）
- （加分，不打包）QUIC/FEC/ARQ/BBR：标注「未来可扩展」，不破坏主线。

## 6. 边界 / 不做（防 scope 蔓延）
- 第一版只做 TCP 长连接 + 二进制协议；UDP/QUIC 全当加分层。
- 不做真正的 UI 线程整合（只暴露 listener 接口 + 自测 demo 轮询消费）。
- 不做鉴权/加密（可作为最后一节讨论点）。
- 不做多 server 集群 / 消息持久化（后者留给 kv-engine 回接）。
